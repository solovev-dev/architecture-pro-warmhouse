### 1. Описание функциональности монолитного приложения
**Управление отоплением:**
- Пользователи могут удалённо управлять отоплением в своих домах путем взаимодействия с датчиком:
    - Включение/отключение устройства отопления;
    - Установка целевой температуры устройства отопления.
- Система поддерживает управление устройствами отопления в домах:
    - Регистрация нового датчика;
    - Редактирование параметров датчика;
    - Удаление датчика.

**Мониторинг температуры:**
- Пользователи могут проверять показания температуры в своих домах.
- Система поддерживает получение данные о температуре:
    - Для зарегистрированных в системе датчиков (все сразу или идентификатору датчика);
    - В определенной локации по идентификатору локации.
### 2. Анализ архитектуры монолитного приложения
#### Допущения
Описание системы и предоставленный код не дают исчерпывающего понимания контекста и границ системы. 
Нет информации о том как физически устроена система управления отоплением, как осуществляется взаимодействие с ней и управление домами. 
Поэтому сделаю ряд предположения об устройстве системы:
1) Для управления отоплением компания использует термостаты с встроенным датчиком температуры (например, `Sonoff TRVZB`)
2) В каждом доме клиента развернуть локальный сервис (например, на микроконтроллере `Raspberry Pi`). 
Пусть это будет сервис **temperature-api**. Сервис общается по протоколу MQTT (`Zigbee2MQTT` для нашего термостата `Sonoff TRVZB`) и предоставляет 
внешний REST API для запросов:
    - `GET /temperature?location=:location` - текущая температура в помещении
    - `GET /temperature/:sensorId` - установленная температура на термостате
    - `POST /temperature/:sensorId/target` - установить целевую температуру. **Сейчас нет такой ручки**, но нам необходимо как-то управлять температурой и включение/отключением отопления.
3) Доступ до локального сервиса `temperature-api` в доме клиента сервис `smart home` осуществляет через `Cloudflare Tunnel` с `Service Token` либо любое другое решение для защиты сетевого доступа.
В крайнем случае на роутере настроен проброс портов для доступа через интернет. 
4) Маршрутизация запросов между домами происходит в сервисе `Smart Home`. Допустим, что где-то есть конфигурация `customer_homes` с информацией `homeId` + `tunnel_host`, а в 
таблице `sensors` есть поле `homeId`, которое заполняется при настройке датчика специалистом компании.

#### Общее
С учетом сделанных допущений приложение представляет собой монолит `smart home` и локальные адаптеры `temperature-api` 
для общения с системой отопления.
В текущем решении не хватает логики маршрутизации между домами и передачи команд на термостаты (датчики).  

#### Стек:
- **Язык программирования:** Go
- **База данных:** PostgreSQL 16 Alpine
- **Управление зависимостями:** Go Modules 
- **Сборка и развертывание:** Multi-stage Dockerfile + Docker Compose

#### Архитектура:
Монолитная архитектура. Все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения. 
Для организации кода не используется какой-либо из приемов (например, гексогональная аритектура).  
Сама система состоит из двух сервисов:
    - `smart-home` - обработка запросов, бизнес-логика, работа с данными
    - `temperature-api` - сервис адаптер для управления устройствами в доме. В проекте есть только заглушка к клиенту. 
- **Взаимодействие:** Синхронное, запросы обрабатываются последовательно. Получение данные о датчиках и обработка команд тоже синхронное.
- **Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.

Условная схема всей архитектуры системы as is с учетом сделанных 
допущений может выглядеть так: [Architecture](diagrams/monolith/architecture/SmartHome_Schema.png).

### 3. Определение доменов и границы контекстов

#### Ubiquitous Language
- Устройство - может включать в себя реле и несколько датчиков или только реле/датчик

- Реле - переключатель, который автоматически замыкает или размыкает электрическую цепь

#### Problem Space
**Core Domain: Умный дом**

**Core Subdomains:**
- Поддомен управления устройствами (команды и состояние)

- Автоматизация и сценарии (настройка различных программируемых сценариев)

**Supporting Subdomains:**
- Поддомен устройств - подключение к экосистеме + реестр модулей/устройств

**Generic Subdomains:**

- Поддомен профиль пользователя
- Поддомен доставки
- Поддомен аудит/логирование

- Управление устройствами (в том числе протоколы/подключения к устройствам)
- Подключение к экосистеме и настройка устройств
- Автоматизация и сценарии
- Телеметрия
- Управление домом и пространством, подключение устройств
- Коммерция (продажа устройств, платежи, доставка)

### 4. Проблемы монолитного решения
* **Синхронное взаимодействие:** Все запросы обрабатываются последовательно. Всё управление идёт от сервера к датчику. Данные о температуре также получаются через запрос от сервера к датчику.
- **Устойчивость к отказам:** Низкая отказоустойчивость, так отказ сервиса приведет к отказу всего приложения - всей функциональности.
* **Масштабируемость:** Ограничена, так как не можем масштабировать по частям. Функциональность продажи модулей, управления устройствами и мониторинг показаний датчиков имеют разный профиль нагрузки, но не смогу масштабироваться по частям при кратном росте клиентской базы.
- **Сложность управления командой:** Все компоненты приложения объединены в единый блок. Чтобы внести изменение или добавить функциональность, нужно внести изменения во всё приложение. Задачи, которыми будут заниматься разные команды, могут блокировать друг друга. Текущий лэндскейп проекта уже позволяет организовать несколько небольших команд разработки для работы. Монолит не позволяет изолировать их между собой.
- **Гибкость в выборе технологий:** Текущее решение использует один язык программирования и ограничивает выбор технологического стека.
- **Развертывание:** Требует остановки всего приложения.

Ограничения текущего решения: 
1) Нет буферизации на стороне `temperature-api` - при отсутствии интернета теряем показания с датчика. 
2) Синхронный опрос устройств. При кратном росте устройств будет ряд последовательных HTTP-запросов к датчикам.
3) Нет покрытия тестами

# Задание 4. Создание и документирование API

### 1. Тип API

Взаимодействие сервисов внутри SmartHome гибридное: как синхронное, так и асинхронное. 

#### Отправка команд на устройства
Асинхронное API (с синхронным подтверждением):

`DeviceControlService` - принимает команду по HTTP/REST (валидация, авторизация, журнал), публикует в CommandQueue и отдаёт вызывающему commandId + статус PENDING/PUBLISHED.
`HomeHubService` - читает команды из очереди, исполняет на устройствах (MQTT) и возвращает результат исполнения (APPLIED / FAILED).
`DeviceControlService` — обрабатывает подтверждение (ApplyCommandResult), обновляет журнал команд и состояние устройства.

Обоснование:
- **Надежность.** Дом или Hub могут быть offline: команда сохраняется в очереди и доставляется при появлении связи, а не теряется по таймауту синхронного HTTPS через tunnel. 
Статусы PUBLISHED → APPLIED/FAILED дают явное подтверждение исполнения, а не «успех» только на уровне HTTP до Pi.
- **Масштабируемость.** Синхронный путь «облако → Cloudflare Tunnel → temperature-api → устройство» на каждую команду не масштабируется с ростом домов.
- **Безопасность.** Сейчас облако инициирует вход в домашнюю сеть на каждый опрос. Асинхронный вариант убирает эту необходимость
  и сужает атакуемую поверхность и использование service token’ов.

#### Получение телеметрии 
Асинхронное API:

`HomeHubService` - пишет поток событий из дома клиента. 
`TelemetryService` - читает и обрабатывает поток событий (отправляет подтверждения о смене состояния устройств и показания датчиков)

Обоснование: 
- **Надежность.** Дом может быть offline, асинхронный обмен + локальная буферизация позволяют дослать данные позже без потерь. 
Если SaaS экосистема в облаке недоступна, то телеметрия так же не будет утеряна.
- **Масштабируемость.** Синхронный опрос N датчиков/домов не масштабируется; поток в Kafka и отдельный TelemetryService масштабируются независимо от других сервисов. 
- **Безопасность.** Сейчас облако инициирует вход в домашнюю сеть на каждый опрос. Асинхронный вариант убирает эту необходимость 
для телеметрии и сужает атакуемую поверхность и использование service token’ов.

#### События Bounded Context-ов:

Асинхронные API:

Публикация доменных события внутри BC через Kafka.

Обоснование: 
 - **Факт уже случился, синхронный ответ не нужен.** Все межсервисные события о фактах произошедших внутри домена не требуют ответа издателю 
(например, Commerce завершил доставку; ему не важно, успел ли DeviceManagement создать запись в ту же миллисекунду), 
 - **Слабая связность и независимое развитие.** Издатель не знает список подписчиков. Можно независимо добавить потребителей событий, 
не внося изменения в сервис-издатель. 
 - **Отказоустойчивость системы.** Если сервис-потребитель временно недоступен, это не блокирует работу сервиса-издателя. При синхронном варианте
взаимодействия сценарий сломался бы.

#### Запрос-ответ взаимодействие (между сервисами)
Синхронный REST API: 

Используем для взаимодействия клиент -> платформа, сервис -> сервис.

Обоснование:

Завершение операции обязательно требует получения ответа от поставщика. Потребитель явно зависит от контракта поставщика и ждёт результат. 
Например, различные CRUD операции, оформление заказа и настройка домов/комнат/ролей.

# **Задание 6. Разработка MVP**

Необходимо создать новые микросервисы и обеспечить их интеграции с существующим монолитом для плавного перехода к микросервисной архитектуре. 

### **Что нужно сделать**

1. Создайте новые микросервисы для управления телеметрией и устройствами (с простейшей логикой), которые будут интегрированы с существующим монолитным приложением. Каждый микросервис на своем ООП языке.
2. Обеспечьте взаимодействие между микросервисами и монолитом (при желании с помощью брокера сообщений), чтобы постепенно перенести функциональность из монолита в микросервисы. 

В результате у вас должны быть созданы Dockerfiles и docker-compose для запуска микросервисов.

### **Что сделано**

**Сервисы:**
- `device-control` (Python / Flask) — управление устройствами, хранение в PostgreSQL
- `telemetry-service` (Java / Spring Boot) — реестр устройств и телеметрия в TimescaleDB
- Kafka (`confluentinc/cp-kafka`) + ZooKeeper — асинхронная шина событий

**Схема взаимодействия:**

```
Monolith (8080) ──create sensor──► Kafka topic device-events
Device-Control (8082) ──create device──► Kafka topic device-events
                                              │
                                              ▼
                                   Telemetry Service (8083)
                                   ├─ регистрирует устройство в TimescaleDB
                                   └─ device-telemetry → сохраняет, только если устройство есть
```

При создании сенсора в монолите или устройства в `device-control` публикуется событие `device.created`. `telemetry-service` регистрирует устройство; телеметрия из топика `device-telemetry` сохраняется только для известных устройств.

**Идея миграции с монолита.** Новые устройства сразу ведутся через `device-control` и `telemetry-service`, без расширения монолита. Уже существующие сенсоры, создаваемые в `smart_home`, через Kafka тоже попадают в реестр телеметрии — оба контура сходятся в одном сервисе. Это даёт единый поток телеметрии и позволяет постепенно, без «большого взрыва», переключить пользователей с монолита на микросервисную архитектуру: сначала общий реестр и данные, затем — полное управление устройствами в новых сервисах.

### **Как проверить**

```bash
cd apps
docker compose up --build -d
```

1. Health-check:
```bash
curl http://localhost:8080/health   # monolith
curl http://localhost:8082/health   # device-control
curl http://localhost:8083/health   # telemetry-service
```

2. Создать сенсор (монолит → `device-events`, id вида `sh-1`):
```bash
curl -X POST http://localhost:8080/api/v1/sensors \
  -H "Content-Type: application/json" \
  -d '{"name":"Test Light","type":"light","location":"Kitchen"}'
```

3. Создать устройство (device-control → `device-events`, id вида `dc-1`):
```bash
curl -X POST http://localhost:8082/api/v1/devices \
  -H "Content-Type: application/json" \
  -d '{"name":"Kitchen Thermostat","type":"temperature","location":"Kitchen","state":"off"}'
```

4. Проверить регистрацию устройств:
```bash
curl http://localhost:8082/api/v1/devices
curl http://localhost:8083/api/v1/devices
```

5. Отправить телеметрию в Kafka и прочитать результат:
```bash
echo '{"deviceId":"sh-1","timestamp":"2026-10-17T18:40:00Z","metric":"temp","value":20.0,"unit":"C"}' \
  | docker exec -i smarthome-kafka kafka-console-producer \
```
